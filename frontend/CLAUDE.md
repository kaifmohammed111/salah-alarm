# SalahSync — Project Knowledge (CLAUDE.md)

This file is the entry point. Read this first, then `docs/architecture.md`, `docs/current-status.md`, and `docs/known-issues.md` for depth. Together these four files are meant to let a brand-new session continue this project without any prior chat history.

## What This Project Is

SalahSync is a React Native / Expo (SDK 54) Islamic prayer-timetable, alarm, and companion app (Qibla compass, Dhikr counter, Quran reader/player, How to Pray guide) for Android (iOS/web are configured but untested/unused — all real development and testing has been Android-only, on a physical Vivo device).

- **Repo**: `github.com/kaifmohammed111/salah-alarm`
- **Working directory**: `frontend/` (the repo root has other things in it; always `cd frontend` first)
- **Android package**: `com.emergent.salahalarm.lxw9zs` (a rename to a permanent name/package is planned but **not yet started** — see `current-status.md`)
- **EAS project**: `kaif0121/projects/frontend`
- **There is no backend, no database, no remote API.** Everything is client-side. All "persistence" is `AsyncStorage` via `src/utils/storage.ts`. If asked to document "the API" or "the database schema," the honest answer is that neither exists. The closest things to external APIs are two read-only third-party services consumed by the Quran feature, and Google's AdMob SDK (ads) — see `architecture.md`.

## The Person You're Working With

Non-developer or early-developer working entirely through copy-pasted terminal commands in WSL Ubuntu, driving an AI assistant to build and iterate a real app. They do not read or write code themselves — every file is generated by Claude, copied from Windows Downloads into the WSL repo via `cp`, and built via a scripted sequence they paste verbatim. This has strong implications for how to work on this project (see "How This Project Actually Gets Built" below) — it is not enough to write correct code, the interaction pattern itself has recurring failure modes that must be actively guarded against.

## Environment & Build (read this before doing anything else)

- WSL2 Ubuntu, repo cloned at `~/salah-alarm` on WSL's **native filesystem**, not under `/mnt/c/...` (moved off C: drive after it filled up, now lives on a WSL distro stored on D:). Path matters for native build performance/correctness.
- Windows Downloads folder (where generated files land for the person to `cp` into the repo) is **`/mnt/d/Downloads/`**, not the default `/mnt/c/Users/<user>/Downloads`. This has caused real failed-copy incidents — always confirm the actual path if anything seems off.
- `adb` is accessed via Windows-side platform-tools: `"/mnt/c/RSL/platform-tools/adb.exe"` (note the `.exe`, and it must be quoted because of the space-containing path when invoked from certain contexts — always use the exact quoted form).
- **Builds are local only** — the EAS free cloud-build tier is exhausted. Every build is:
  ```bash
  cd ~/salah-alarm/frontend
  eas build -p android --profile preview --local
  "/mnt/c/RSL/platform-tools/adb.exe" install -r "$(ls -t *.apk | head -1)"
  ```
  A full local build (especially after `rm -rf android`) typically takes 5–10 minutes with **no visible output** unless you tail the log — do not assume it's stuck.
- **Any time a config plugin (`plugins/*.js`) or `app.json` plugin/permission config changes, run `rm -rf android` before rebuilding.** Otherwise stale generated native files can linger and silently not reflect the change. This also applies whenever a *native* dependency (not pure JS) is added/removed/changed — e.g. `react-native-svg`, `react-native-google-mobile-ads`.
- New npm packages: `npm install <pkg>` (or `npx expo install <pkg>` for Expo-managed native modules) must be run **inside WSL**, not edited by hand in `package.json` alone, or the native module won't actually be present for the build.
- Git auth is PAT-based (`git config --global credential.helper store`), already configured.
- `.gitignore` includes `*.apk` and `*.txt` — build artifacts and log dumps should never be committed (this leaked into git once and was cleaned up).
- Transient `request to https://api.expo.dev/graphql failed` errors are common and usually resolve on retry.
- **`android/` is a generated, disposable directory.** It does not persist reliably across sessions — sometimes it exists from a prior `expo prebuild`, sometimes it's been wiped. Always confirm with `ls android` (or equivalent) before assuming it's there, and regenerate with `npx expo prebuild --platform android` if needed for direct `gradlew` debugging (see "Debugging native build failures directly" in `architecture.md`).

## How This Project Actually Gets Built (critical process knowledge)

This is not obvious from the code and has caused real, repeated time loss. Internalize this before making changes.

### 1. Every file change goes through a manual copy step — verify it landed
Claude generates a file → person downloads it → runs `cp /mnt/d/Downloads/<file> <repo-path>`. This step silently fails more often than expected (stale cached download, wrong file, `cp` from the wrong source). **Every `cp` must be immediately followed by `grep -c` on a distinctive string unique to the new content**, and Claude should state the exact expected count. When a person reports a count that doesn't match Claude's own file, **check Claude's own generated file's real count first** — several apparent "copy failures" this project turned out to be Claude misremembering/miscounting its own expected value, not an actual copy problem. Don't assume the person did something wrong before checking your own arithmetic.

### 2. Never trust a session summary's claim that something was "implemented"
This has happened more than once: a prior session's summary described a fix or feature as complete, but a fresh `cat`/`grep` of the person's actual current file showed it had never actually been applied. **Before building on top of any previously-described work, re-view the actual current file.** This is a stronger warning than usual "don't assume" advice — it has concretely wasted real time on this project (dhikr rewrite, `countdownAnchor` fix, modal scroll fix, and — most recently — the entire "How to Pray" fiqh-segments/Qunut/Fard-only-tappable feature, which the person asked follow-up questions about before ever actually applying the file that introduced it, all fell into this trap).

### 3. `str_replace`/anchor-based edits fail silently on invisible whitespace — always verify with a fresh view first
The single most common cause of a "MISMATCH: anchor not unique" or a Python patch script failing was an anchor text that looked identical on screen but had a blank line, or slightly different surrounding context, that wasn't accounted for. **This happened repeatedly across the whole project, including multiple times in the same session** (the Settings "Madhab" section was accidentally duplicated this way — a patch script's anchor pattern matched both before *and* after a first successful run, because the "old" text it searched for was still present, unchanged, right after the newly-inserted content). **Mitigation that actually works**: before writing a patch script against a file that's been edited several times already, get a *fresh* `sed -n` or `cat -A` dump of the exact region being changed — don't reuse an anchor from several turns ago on the assumption the file hasn't drifted.

### 4. Guessing without evidence has reliably wasted more time than it saved
For anything that fails silently — wrong value shown, feature not triggering, no visible error — the fix has consistently been: add a targeted `Log.d` (Kotlin) or `console.log`/non-silent error handling (JS), get the person to reproduce while capturing `adb logcat`, then grep the relevant tag; or, for build failures, get the *exact* compiler error text (`grep -n "^e:"` on a raw gradlew log, not just the EAS summary) before proposing a fix. Concrete examples where this was the only thing that actually worked: the widget countdown bug, the widget auto-advance bug, and — this session — the AdMob Kotlin compilation failure (root cause was only found by running `gradlew` directly with `--stacktrace` and grepping for `^e:`, since EAS's own build log summary never showed the real Kotlin compiler error at all).

### 5. Native/library research: verify against real, current documentation and source before committing to an approach
Multiple points in this project involved assuming a library's API/behavior from general training knowledge, which turned out wrong on inspection. The pattern that worked: when a build or runtime failure is unexplained, search for the *exact* error text before proposing a fix, and when official docs are ambiguous, check the library's actual installed source/type definitions on disk (`node_modules/`) rather than relying on memory. This session, a genuinely thorough real-world example: the AdMob "incompatible Kotlin version" error was root-caused by finding an exact-match GitHub issue on the library's own repo (maintainer-confirmed fix: pin to an exact older version), not by guessing at dependency version numbers — an earlier attempt at guessing version numbers to bisect (`resolutionStrategy { force ... }`) technically worked as a diagnostic exercise but was correctly abandoned in favor of the maintainer's actual documented fix once it was found.

### 6. Never guess at native Android Activity/Intent internals without verified evidence — a real regression happened this way
This session, an attempt to fix a full-screen-alarm timing issue by pointing Notifee's `launchActivity` at a custom native Activity (instead of `"default"`) **broke notification-tap entirely** — confirmed by the person reporting tapping the notification did nothing at all, a regression from previously-working behavior. The fix was reverted immediately once this was discovered, and no fully-verified correct format for a custom `launchActivity` string was ever found (Notifee is now archived/unmaintained — see `known-issues.md`). **Lesson: for anything touching how notifications launch Activities, treat it as safety-critical (this app's whole purpose is waking someone for prayer) and verify a working example exists before shipping, don't reason from API shape alone.**

### 7. Pause and ask before large, costly architectural pivots or large scope expansions
When a chosen approach turns out to require significant additional scope (e.g., a "quick" library swap that turns out to need writing an entire custom native module; or a content feature that starts as "one screen" and organically grows into a multi-level navigation structure with fiqh-specific data), stop and lay out the real trade-offs for the person to decide, rather than unilaterally continuing to sink further build cycles into one path. This project has a real cost per iteration (5–10 minute local builds, no cloud fallback), so this matters more than it would in a typical fast-feedback-loop project. This session's "How to Pray" feature is a good example of doing this correctly: scope was explicitly checked and re-checked at several points (four-madhab granularity vs. simplified split, 3D vs. 2D illustrations vs. real generated images, all-9-prayer-types vs. daily-prayers-first, full segment structure vs. Fard-only) rather than assumed.

## Quick Reference: Key Commands

```bash
# Standard build/install cycle
cd ~/salah-alarm/frontend
git add . && git commit -m "..." && git push
eas build -p android --profile preview --local
"/mnt/c/RSL/platform-tools/adb.exe" install -r "$(ls -t *.apk | head -1)"

# Config plugin or app.json plugin/permission change, or any native dependency
# add/remove/version-change? Do this first:
rm -rf android

# Logcat capture-and-grep (the single most effective debugging tool on this project)
"/mnt/c/RSL/platform-tools/adb.exe" logcat -c
# ... person reproduces the issue on-device ...
"/mnt/c/RSL/platform-tools/adb.exe" logcat -d > capture.txt
grep -i "YourTag\|ReactNativeJS\|FATAL EXCEPTION" capture.txt

# Verify JSON after any app.json edit
python3 -c "import json; json.load(open('app.json')); print('valid JSON')"

# Verify a copied file landed correctly (always do this after every cp)
grep -c "SomeDistinctiveString" path/to/copied/file

# Debugging a native (Gradle/Kotlin) build failure directly — much faster than a full
# eas build --local cycle, and shows the REAL compiler error EAS's own summary often hides
npx expo prebuild --platform android   # regenerate android/ if it doesn't currently exist
cd android
./gradlew :some:task:name --stacktrace --no-daemon --rerun-tasks > /tmp/build_log.txt 2>&1; echo "DONE, exit code: $?"
grep -n "^e:\|error:" /tmp/build_log.txt   # the actual compiler diagnostic, not just the summary
```
